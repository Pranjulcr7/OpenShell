## Cases

The REST and admitted-MCP cases send the same `POST /mcp` request, host, port,
headers and `tools/call` body. Both use the existing successful token grant
fixture, configured to return a synthetic bearer token for that endpoint.
REST admits the HTTP method/path; MCP admits the `read_status` tool under the
`2025-03-26` protocol profile.

| Case | HTTP result | Grant resolver calls | Forwarded request | Test |
| --- | --- | --- | --- | --- |
| Allowed MCP `read_status` | Fixture's 204 | 0 | Body preserved; no Authorization header | Fails: expected one grant |
| REST control, same request | Fixture's 204 | 1 | Body preserved; exactly one expected bearer header | Passes |
| Denied MCP `delete_resource` | Relay's 403 | 0 | No bytes forwarded | Passes |

The upstream fixture returns 204 whenever it receives a complete request;
it does not authenticate requests. The captured upstream headers and resolver
call count demonstrate the missing grant on the MCP path.

The tests exercise `relay_with_inspection` with the actual parser and policy
engine, in-memory duplex streams and the existing fake `TokenGrantResolver`.
No live credential broker, SPIRE service, TLS handshake or sandbox is involved.
This isolates relay behavior; it is not an end-to-end deployment test or full
coverage of the issue's acceptance criteria.

The production code is unchanged. The existing REST path calls
`token_grant_injection::inject_if_needed`; the admitted MCP path in
`relay_jsonrpc` forwards without that call. The separate route-selection path
discussed in #3657 is outside this reproduction.

Both modified Rust files pass `rustfmt --check`; `git diff --check` also passes.
